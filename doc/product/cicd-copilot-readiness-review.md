# CI/CD Epic #1 -- Copilot Coding-Agent Readiness Review

## Verdict

- **Overall: GO with conditions.** The build lane is dispatchable now; do not fan out beyond docs until the four blocker fixes land and the template-sync round-trip to partition is green.
- **Build lane: GO with conditions.** Runs under `GITHUB_TOKEN`, no open gate; fix the three stale issue bodies (#19, #3, #22) and the W10/#8 merge-hold encoding first.
- **Deploy lane: NO-GO (draft-only).** May be authored as draft PRs but must not merge until Phase 0 gate 0e closes, the manual PoC runs and is recorded in `cicd-poc-notes.md`, and `oidc-smoke-test.yml` (a #11 deliverable, not yet on disk) runs green on partition for branch+tag subjects.

The dependency graph is sound -- verification found no cycles, every hard edge is reflected by a `blocked`/`phase0-blocked` label, and the two-PR credential cut (Build under `GITHUB_TOKEN`, Deploy acquiring Azure federated identity) is the correct go/no-go axis. The real kickoff risk is not missing prerequisites but **stale source-of-truth docs that will yield wrong-but-plausible PRs**: #19's acceptance criteria direct the agent to edit `docker-build`/`deploy`/`integration-test` `if:` clauses that do not exist in `validate.yml` yet (it has only four jobs), directly contradicting the plan's "no `if:` clause changes" scope. The single largest systemic gap is that `.github/copilot-instructions.md` never tells the agent it **cannot exercise this pipeline in this repo** -- there is no `pom.xml`/`Dockerfile`/provider dir, `validate.yml` paths-ignores the very files being edited, and the only required check is CodeQL -- so for ~14 author-only issues a clean draft PR is zero runtime proof, and the agent will report un-runnable work as done. Two metadata foot-guns compound this: ONBOARD-INIT-A/#21 is labeled `ready-to-fire` but tells the agent to read operator inputs from an `init.yml` `workflow_dispatch` UI that does not exist (real `init.yml` is `on: push` with a single issue-comment channel), and W10/#8 carries "Blocked by: None" while its body forbids merge until partition is green. Verification refuted the headline claim that "all five Phase 0 gates are open" -- the epic body shows 0a/0b/0c/0d/0f resolved and only **0e** open -- so the deploy lane's draft-only constraint is real, but it is a merge gate, not a kickoff gate. Fix the four blockers below and the build lane fans out immediately.

## Blockers -- fix before kickoff

These four survived adversarial verification (`isReal:true`). Verification **refuted** the originally-proposed blockers B2 (#3 artifact contract), B4 (#8 label/body), B6 (deploy-lane merge gate), B7 (#12/#26 stubs), and B9 (#24) -- those are tracked under Should-fix, not here.

1. **W13/#19 acceptance criterion directs edits to jobs that do not exist.**
   *Affected:* #19 (primary), #22, #6. *Owner:* design-author.
   #19 AC#2 reads verbatim "The new `docker-build` / `deploy` / `integration-test` jobs' `if:` clauses recognize the input." Those jobs are **not** in `.github/template-workflows/validate.yml` (it contains only `check-initialization`, `check-repo-state`, `java-build`, `code-validation`); they are W5a/#22 and W5b/#6 deliverables (both OPEN). The canonical plan (`cicd-implementation-plan.md` L1105) says the opposite: "**No `if:` clause changes in this PR.** The `|| (workflow_dispatch && force_full_pipeline)` half ... lands with W5a (#22) ... and W5b (#6)." #19 is `ready-to-fire` with no `blocked` label, so the harm is live: a dispatched agent will either stall on an unsatisfiable checkbox or invent `docker-build`/`deploy`/`integration-test` jobs in `validate.yml` -- a direct scope collision with W5a/W5b on a serialized hot file. **Fix:** rewrite #19's body to match plan L1100-1105 -- delete AC#2 and replace with the "no `if:` changes; input is inert until referenced" wording; collapse the "README or in-file comment" AC to in-file comment only (no README exists in `template-workflows/`); repoint the Reference from "lines 41-58 (paths-ignore)" (L41 is actually the `push:` key) to the `workflow_dispatch.inputs` block (L59-70); reconcile the "Out of scope" line so modifying **any** job `if:` clause is out of scope.

2. **The canonical §5.5 trust-boundary `if:` clause has three non-identical forms across the docs.**
   *Affected:* #6, #22 (and design §5.5 / plan / Appendix A.1). *Owner:* design-author.
   Design §5.5 (L513-515) requires `needs.check-initialization.outputs.initialized == 'true' && needs.check-repo-state.outputs.is_java_repo == 'true' && needs.java-build.outputs.build_result == 'success' && ...`. The plan's W5a/W5b blocks (L399, L448) and the Appendix A.1 excerpt (L1579, L1602) carry **only** `build_result == 'success' && ...` and omit the two guards plus their `needs:` entries. The epic's agent-rule says "the W5b `if:` clause is the canonical form -- do not weaken," but the agent has three different targets and no in-repo way to choose; a security reviewer comparing any choice to §5.5 will bounce it. **Fix:** pick ONE canonical clause and make design §5.5, plan W5a/W5b, and #6/#22's ACs byte-identical (either re-add the two guards everywhere, or intentionally document their omission and note `build_result` already implies them since it `needs` the upstream jobs). Mark Appendix A.1 illustrative-only and superseded by the AC for `needs`/`if`/login placement; state once whether `deploy`/`integration-test` re-assert init/java-repo or rely on `docker-push` skip-propagation.

3. **`copilot-instructions.md` never states the build-here / validate-on-partition split.**
   *Affected:* the ~14 author-only issues (#3, #4, #5, #6, #7, #8, #9, #10, #11, #20, #21, #22, #24, #25). *Owner:* design-author.
   Grep of `.github/copilot-instructions.md` (188 lines) finds zero mentions of "partition," "validate on," "cannot test," or "not run here." This repo has no `pom.xml`/`Dockerfile`/provider dir; `validate.yml`'s paths-ignore excludes `.github/template-workflows/**` and `.github/actions/**` on all triggers; the only required check is CodeQL; there is no active `copilot-setup-steps.yml` (only the `fork-resources` copy). So a PR editing these deliverables gets **no runtime signal** here, yet nothing tells the agent so -- it will treat clean draft PRs as "done." The credential-boundary and hot-file rules are present; this load-bearing fact is the gap. **Fix:** add a "Where CI behavior is validated" subsection to `copilot-instructions.md`: this is the template repo (no service code); edits under `.github/template-workflows/` and `.github/actions/` execute only on service forks (e.g. partition) via template-sync; a clean draft PR here means "YAML parses + logic reads," **not** "pipeline ran green"; require every PR body to add a "Validation -- what must be checked on partition" section, and for deploy-lane PRs to open as draft and enumerate every cluster/auth assumption (RoleBinding subject form, deployment/container names, gateway URL, federated-identity subject claim). The plan already says (L169) to merge updated `copilot-instructions.md` before bulk-launch -- this rides that gate.

4. **ONBOARD-INIT-A/#21's operator-input mechanism does not exist, yet #21 is `ready-to-fire`.**
   *Affected:* #21 (primary), #24. *Owner:* design-author.
   #21's ACs and design §9.4.B/C tell the agent to read `SERVICE_NAME`/`MAVEN_PROFILE` "from `init.yml` inputs" via a "`workflow_dispatch` UI." Verified: `.github/workflows/init.yml` is `on: push` only (no `workflow_dispatch`, no `inputs:`); the only operator-input channel is a single issue-comment line parsed by `validate-upstream-repo` (`head -1`, one token). `setup-service-variables.sh` has no source for its values. The agent hits an undesigned fork on its first action -- it must invent a mechanism (add `workflow_dispatch`, which collides with the `on: push`→issue→comment architecture; extend the comment parser; or derive from repo name), each with different correctness and UX. **Fix:** before dispatch, write the concrete mechanism into #21 and design §9.4.B/C. Recommended: operator supplies values as additional labeled lines in the same initialization-issue comment; extend the parser to pass them to `setup-service-variables.sh` from `init-complete.yml`. Also specify that new helpers run as inline `/tmp/init-helpers/*.sh` steps after "Setup Repository Rulesets" (the `.github/local-actions/` tree is deleted before the post-push phase, so wiring via `action.yml` would silently no-op), `cp`'d into the temp-preservation block; pin the `SERVICE_NAME` (default = repo basename) vs `MAVEN_PROFILE` (operator-required, no safe default) contract; and **drop `ready-to-fire`** from #21 until the mechanism is written.

3. **Metadata is consistent on its load-bearing edges but drifts on *why* things are gated.** No cycles, every hard dep gated -- but stale `phase0-blocked` labels (epic shows only 0e open), a `ready-to-fire` label on the merge-held W10, and soft-W2 dependents co-waved without an "integrate-after" note. 4. **The Build/Deploy credential cut is the right go/no-go axis.** Build runs under `GITHUB_TOKEN` with no open gate (dispatchable now); Deploy is draft-only until 0e closes, the PoC runs, and `oidc-smoke-test.yml` runs green -- plus the cross-repo `osdu-spi-stack#32` that single-repo labels can't track.
5. **Trust-boundary PRs are the highest blast radius.** `pull_request_target` is already live in `validate.yml` and propagates to all forks, so a wrong `if:` clause in #22/#6 ships a credential-exposure path everywhere at once. Exclude #22/#6/#19 from auto-merge; mandatory security review against §5.5; serialize `validate.yml` edits.

## Verifying author-only work

The build-here / validate-on-partition split is the structural reality of this repo: `osdu-spi` is the engineering-system template with **no service code** -- no `pom.xml`, `Dockerfile`, or provider dir -- and its CI workflows (`.github/template-workflows/`) and composite actions (`.github/actions/`) only execute after `template-sync` propagates them to a service fork such as `danielscholl-osdu/partition`. `validate.yml`'s paths-ignore excludes those exact directories on every trigger, and the only required status check is CodeQL, so a PR editing the deliverables fires no functional CI here. A green draft PR therefore proves only "YAML parses and the logic reads correctly," never "the pipeline ran."

For the ~14 author-only issues, the orchestrator closes the loop the agent cannot: after a PR merges into the sandbox, the operator triggers a validation run on partition (via `workflow_dispatch`, since template-sync changes are paths-ignored -- this is exactly what W13/#19's `force_full_pipeline` input exists to enable) and confirms the runtime contract there -- e.g. for #3, that `push:false` skips GHCR login and the digest composes as `${image_repository}@${image_digest}` with a single `sha256:` prefix; for #22, that the trusted/untrusted job split behaves and the `🐳 Docker Build` required check passes; for deploy-lane code, that `kubectl set image` lands and integration tests run against the live gateway. To make this auditable, every author-only PR must carry a "Validation -- what must be checked on partition" body section (enforced via B5 + the PR template), and the wave board must record each issue's partition run URL (or "N/A") before its merge gate opens -- so "clean PR here" is never mistaken for "validated."
